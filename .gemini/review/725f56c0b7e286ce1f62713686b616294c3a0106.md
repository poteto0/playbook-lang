## Findings

### Medium — no regression test for the front-end error envelope
The issue's checklist requires "Renderer / CLI output paths use the new error's `message()`". The wiring is structural (`format_ir_error` is generic over `message()`/`span()`, and `render`, `play`, and the CLI all route through it), but no test asserts a duplicate-action input surfaces `Duplicate action 'move' for 'p1' ...` through the `[Error]:[...]` envelope with the duplicate entry's line/column. In fact no existing test exercises the IR branch of `CompileError` at all. If `format_ir_error` regressed (e.g. to `Display` with swapped fields), CI would stay green while the frontend breaks.

→ Fix: add a renderer test rendering a duplicate-move playbook and asserting the envelope, message, line and column.

### Medium — cross-kind duplicates are unaddressed and undocumented
The issue's open question — a player holding both a `move` and a `screen` in one block — is intentionally not rejected here, because restricting all cross-kind combinations would also outlaw the legitimate `move` + `pass` (dribble then throw) in one phase: `pass` reads `phase_end_positions`, so the two entries cooperate rather than contradict. That decision is defensible, but the docs added in a54a5f1 don't mention that the rule is per *kind* while cross-kind entries are still accepted today, so readers can't tell a deliberate extension of the language from an oversight.

→ Fix: state the scope explicitly in the docs (per kind; cross-kind like `move` + `pass` remains allowed, `move` + `screen` for the same player is a known-format candidate follow-up tracked by the issue's open questions).

### Low — `kind` is a stringly-typed `&'static str`
A typo (`"mov"`) would compile and produce a subtly wrong message. Accepted as-is: the literals sit in one function, adjacent to the corresponding AST sections, and the message format is asserted in three tests.

### Low — duplicate detection preemts per-entry resolution errors
`validate_action` runs before entry resolution, so in a block containing both an unknown player (`p99`) and a duplicate, the duplicate is reported first. Both outcomes fail loudly with a correct span, and `IRError` reporting is single-error by design (unlike parse errors), so the ordering choice is immaterial.

### Low — `validate_unique`'s closure-driven signature
Generic-over-entry design (with `span_of`/`id_of` closures) is slightly more machinery than the file's other helpers, but it keeps a single implementation for the three keyed lists, in line with the dedupe direction of #105/#106. Call sites read fine.

## Verdict

Approved with the two Medium findings to be addressed before opening the PR.
