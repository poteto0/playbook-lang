# Review of commit f2651984f92e3169bf5f51f706d4b29cb60b482b

## 概要
Arcライン（曲線移動）構文のサポートを追加するコミットです。AST、Parser、IR、Rendererの全レイヤーにわたる変更が含まれています。

## 変更点の詳細
1.  **AST (`core/src/ast/mod.rs`)**
    *   `PathType` および `CurveDirection` Enumを追加。
    *   `MoveAction`, `ScreenAction` に `path_type` フィールドを追加。
2.  **Lexer (`core/src/lexer/mod.rs`)**
    *   `~>`, `~[dir]>` 形式のトークン解析を追加。
3.  **Parser (`core/src/parser/mod.rs`)**
    *   `expect_arrow` メソッドを追加し、直線(`->`)と曲線(`~>`)の両方をパース可能に。
4.  **IR (`core/src/ir/`)**
    *   曲線情報を保持するように `MoveLine`, `ScreenLine` を拡張し、Generatorで値を伝播。
5.  **Renderer (`core/src/renderer/mod.rs`)**
    *   SVGの `path` 要素とベジェ曲線コマンド(`Q`)を使用して曲線を描画するロジックを追加。

## 評価

### 良い点
*   **一貫した実装**: LexerからRendererまで、データの流れが一貫しており、構造的に正しい実装です。
*   **拡張性**: `PathType` Enumを導入したことで、将来的に他の種類のパス（例: ジグザグなど）を追加しやすくなっています。
*   **描画ロジック**: 二次ベジェ曲線（Quadratic Bezier）を用いた制御点の計算ロジック（`calculate_control_point`）はシンプルかつ効果的です。

### 懸念点・改善提案

1.  **構文のキーワードの不一致**
    *   `.gemini/todo.md` やコミットメッセージ（および一般的な期待）では `~[left]>`, `~[right]>` という構文が示唆されていますが、実装（`core/src/parser/mod.rs`）では `l`, `r` という短縮形のみが受け入れられるようになっています。
    ```rust
    match s.as_str() {
        "default" => Ok(PathType::Curve(CurveDirection::Left)),
        "l" => Ok(PathType::Curve(CurveDirection::Left)),
        "r" => Ok(PathType::Curve(CurveDirection::Right)),
        // ...
    }
    ```
    *   **提案**: 可読性向上のため `left`, `right` もサポートするか、短縮形を仕様とするならドキュメント（Todoなど）を更新して統一すべきです。

2.  **マジックナンバーの使用**
    *   `core/src/renderer/mod.rs` の `calculate_control_point` メソッド内で、曲がり具合を決定する係数 `0.3` がハードコードされています。
    ```rust
    let factor = 0.3;
    ```
    *   **提案**: 定数（例: `CURVE_FACTOR`）として切り出すことで、調整が容易になり、意図が明確になります。

3.  **Lexerの柔軟性とParserの厳格さ**
    *   Lexerは `~[...]` の中身を識別子として何でも受け入れますが、Parserで厳密にチェックしています。これは設計として間違っていませんが、Parserのエラーメッセージ `Unknown curve direction: {s}` はユーザーフレンドリーで良いと思います。

## 結論
機能としては要件を満たしており、動作する状態です。ただし、キーワード（`left/right` vs `l/r`）の不一致はユーザーの混乱を招く可能性があるため、早急に統一することをお勧めします。
